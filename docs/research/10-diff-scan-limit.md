# 研究 10：diff 的 scanLimit 与单块退化（P-V2-10）

更新日期：2026-09-29。来源：长链 lc4 阶段 2 发现“3,000 行文件每 50 行改一处，只得到 1 个块”。第 1–6 节为调研与方案（当时只调研，未改产品行为）；用户于同日选择方案 A（[V2-D75](../decisions/v2-decisions.md)），实施结果见第 7 节。

## 结论

- 退化条件取决于**第一处到最后一处改动之间的字符数**，与行数无关：这段区间超过 160,000 个 UTF-16 字符（每行 80 字符时约 2,000 行），而且中间没有足够长的未改动段可供二分时，整段会变成 1 个 change、1 个块。1,000 行以内的常见文件不会退化；3,000 行以上、改动分散的文件（批量改名、格式化、改依赖版本号一类）基本都会退化。
- 退化后显示、块导航、折叠、对齐、词级高亮与 V2-05 块操作都会失效，只是**不会出现误操作**：块操作的执行用的是 Git 的 hunk，显示块与 Git hunk 对不上时直接不提供按钮。
- **不能只是去掉或调大 scanLimit**：去掉后，500 行的整文件重写就超过 20 s；`timeout` 选项也兜不住最坏情况。diff Worker 是单例，并且没有取消机制，卡住一次会让之后所有文件的 diff 都排队等待。
- 分级（先按行比较，再在块内按字符比较）可行：原型在全部测试场景中得到的块与 Git hunk 完全一致，10,000 行以内 ≤ 41 ms；耗时和最坏情况都比现状低，只有 100,000 行的超大文件变慢（187–677 ms，原型未优化）。**推荐方案 A。**
- **已实施方案 A（V2-D75）**：块数与 Git hunk 一致，块操作可用；实施中还修复了阅读器轨道标记 O(块数²) 的强制布局问题。修复后 GUI 未缓存切换 ≤ 193 ms；已缓存切换在 182 块以上时 P95 仍超过 100 ms，记为已知限制。详见第 7 节。

## 1. 机制

`src/diff-core.ts` 调用 `diff(left, right, { scanLimit: 5000 })`（`@codemirror/merge` 6.12.2，逐字符的 Myers 算法，`dist/index.js` 第 44–112 行、第 489–497 行）。scanLimit 自任务 01（`cbb3cf5`，2026-09-22）起就存在，没有相关的决策记录；库内部会先除以 2，即 2500。算法的步骤：

1. 去掉公共前缀与后缀；
2. 一侧是另一侧的子串时直接得出结果；
3. `halfMatch`：找到足够长的公共子串（约为区间的 1/4 以上）时从这里二分，递归处理两半；
4. 否则进入 `findSnake`，受 scanLimit 约束：
   - 较短一侧超过 2500×16 = **40,000** 字符 → 改用粗匹配（`crudeMatch`）；
   - 超过 2500×64 = **160,000** 字符 → **整段直接返回为 1 个 change**；
   - 编辑深度超过 2500 → 改用粗匹配。

`Chunk.build` 只会把 change 扩展到整行，1 个 change 对应 1 个块。附带说明：CodeMirror 合并视图自身的默认值是 `scanLimit: 500`。

## 2. 影响量化

夹具沿用 `scripts/perf/v2-d58-font-equivalence.mjs` 第 60–69 行：每行约 80 字符，每 11 行一行注释。100,000 行改用约 31 字符的短行（3 MiB，处于 5 MiB 文本预算内）。表中为“当前块数 / Git 块数”（Git 块数取自 `git diff --no-index -U0`），**粗体为退化为单块**。

| 规模 | 首尾各 1 处 | 每 500 行 | 每 50 行 | lc4 原夹具¹ | 中部连续 200 行 | 每 5 行 | 整文件重写 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 500 行（34 KiB） | 1/1 | — | 9/9 | 18/18 | 19/19 | 85/85 | 1/1 |
| 1,000 行（68 KiB） | 2/2 | 2/2 | 18/18 | 28/28 | 19/19 | 176/176 | 1/1 |
| 3,000 行（211 KiB） | 2/2 | 5/5² | **1/55** | **1/65** | 19/19 | **1/540** | 1/1 |
| 10,000 行（711 KiB） | 2/2 | **1/18** | **1/182** | **1/192** | 19/19 | **1/1,813** | 1/1 |
| 100,000 行（3 MiB） | 2/2 | **1/182** | **1/1,818** | **1/1,828** | 19/19 | **1/18,176** | 1/1 |

¹ 每 50 行改一个单词，外加一段长行与中部插入的 2 行，即 lc4 阶段 2 的场景（3,000 行时块覆盖第 30 行到末尾共 2,953 行）。
² 没有退化，是因为最后一处改动碰到注释行，实际没有改到，首尾改动之间约 2,000 行、约 14 万字符，低于 160,000，正好印证了上述阈值。

退化为单块之后，各功能受到的影响如下：

| 功能 | 影响 |
| --- | --- |
| 显示 | 块内每一行都加 `oris-modified-line`；唯一的 change 覆盖整段，“按词高亮”时整段都是 `oris-changed-text`，词级高亮失效；工具栏显示“1 处差异” |
| 块导航（F7 / 轨道 / 连接带） | 只有 1/1，轨道标记与连接带各只有一条 |
| 折叠上下文 | 只能折叠块与块之间的未变化行；块内几千行未变化的行都无法折叠 |
| 对齐变化 | 只在块的上、下边界补间隔；块内部两侧逐行漂移（夹具中部插入的 2 行与长行换行之后，右侧越往下越偏） |
| V2-05 块暂存 / 丢弃 | 执行用的是 **Git 的 hunk**（Rust `git/ops/hunk.rs`，解析 `git diff -U0`）；显示块只有在两侧起止行与某个 Git hunk 完全相同时才显示按钮（`src/hunk-model.ts` `matchHunks`）。退化后唯一的块对不上任何 Git hunk，**整个文件都没有块操作按钮**，只显示“与 Git 计算的差异块对应不上……请使用文件级操作”。不会误操作。在所有没有退化的场景中，显示块与 Git hunk 全部对应 |
| 忽略空白（V2-D50） | 唯一的 change 不是纯空白，不会被略去，计数仍为 1 |

## 3. 代价

测量方式：Node 22（V8）中直接调用，与 diff Worker 的算法相同。数值为中位数（ms，含 `Chunk.build`），每个组合单独在一个 worker_thread 中运行，超过 20 s 即终止。WebView2 的 V8 版本不同，只作量级参考；**未做 GUI 端到端测量**。

| 场景 | 当前 | 去掉 scanLimit | scanLimit 50000 | 只设 timeout 300 | 分级原型 |
| --- | --- | --- | --- | --- | --- |
| 3,000 行 lc4 | 2.0（单块） | 66.7 | 63.7 | 62.4 | 5.3 |
| 3,000 行每 5 行 | 2.5（单块） | 92.6 | 92.3 | 88.5 | 10.2 |
| 10,000 行 lc4 | 5.7（单块） | 196.5 | 180.0 | 229.2 | 30.9 |
| 10,000 行每 5 行 | 4.7（单块） | 874.6 | > 20 s | > 20 s | 41.3 |
| 100,000 行 lc4 | 67.5（单块） | 3,787.9 | 69.0（仍单块） | > 20 s | 384.6 |
| 100,000 行每 5 行 | 46.3（单块） | > 20 s | 96.2（仍单块） | > 20 s | 676.7 |
| 500 行整文件重写 | 150–335 | **> 20 s** | **> 20 s** | 309.5 | 28.7 |
| 10,000 行整文件重写 | 8.9 | > 20 s³ | > 20 s³ | 703.5 | 19.0 |
| 100,000 行整文件重写 | 87.6 | > 20 s³ | > 20 s³ | > 20 s | 187.2 |
| 100,000 行首尾各 1 处 | 47.0 | 47.7 | 42.8 | 43.1 | 189.7⁴ |

³ 500 行已经超时，更大的规模不再重复测量。
⁴ 分级原型对每一行都做哈希；先去掉公共的前缀行与后缀行即可避免这部分开销，原型没有做。

- **预算口径**：文件切换预算是端到端的（读取 + diff + 渲染）。已缓存切换（≤ 100 ms）命中 `DiffCache`，不会重新计算 diff，diff 耗时只影响未缓存切换（≤ 400 ms）与预取。现状的最坏情况出现在小文件整体重写：500 行 150–335 ms，已经接近 400 ms。
- **内存**（Worker 堆增量）：当前方案在 10,000 行以内 ≤ 7 MiB，100,000 行约 +43 MiB。去掉 scanLimit 后，10,000 行 +76–84 MiB，100,000 行 +200–230 MiB。分级原型在 10,000 行以内 ≤ 15 MiB，100,000 行 +62–108 MiB（按行建立的 Map 与数组，可以优化）。
- **去掉 scanLimit 的最坏情况**：字符级 Myers 的复杂度约为 O(N·D)，整体重写时 D ≈ N，**500 行就超过 20 s**。diff Worker 是单例（`src/diff.ts`），没有 `terminate`，卡住一次后，之后所有文件的 diff 都要排队等待。
- **timeout 兜不住**：超时之后改用 `crudeMatch`，其中的 `findMatch` 是逐个种子执行 `indexOf` 搜索，本身不受 timeout 约束，100,000 行每 50 行一处时仍超过 20 s。
- **调大 scanLimit** 同时放宽了深度限制与区间长度限制，两者都更容易失控（scanLimit 50000 时 500 行重写超过 20 s），而超大文件照样退化。

## 4. 分级是否可行

可行，也是 Git（xdiff）和 VS Code 采用的思路。调研时的原型写在 `scripts/perf/p-v2-10-scanlimit-probe.mjs` 中（**不是产品代码**；实施后该脚本改为直接调用产品实现，差别见 7.1）：

1. **行级**：每行映射为一个码点；先剔除只在一侧出现的行（这些行必然属于改动，与 xdiff 的 `cleanup_records` 同理，整文件重写因此近乎零成本）；对剩余的行做 diff，得到两侧相等的行对（带 200 ms timeout 兜底，剔除之后编码串很短）；行对之间的空隙就是改动的行区间。
2. **字符级**：只在每个改动区间内做字符级 diff，仍保留 `scanLimit: 5000` 与每个区间 20 ms 的 timeout；总预算 150 ms。区间较短一侧超过 40,000 字符或预算用完时，整段按行标记（不做词级高亮）。

结果：所有场景中块数与“可做块操作”的数量都与 Git hunk 相同（例如 100,000 行每 5 行 18,176/18,176），词级 change 数与“去掉 scanLimit”的结果相同。返回结构不变（`changes` / `hunks`），R-DIFF（计数、高亮、导航出自同一份结果）与 V2-D50（忽略空白作用在区间内的字符级 change 上）的语义不变。

需要注意的差别与风险：

- 行级对齐之后，跨行的字符级对齐（例如一行拆成两行）显示为整行替换。`Chunk.build` 本来就按行划分块，影响很小。
- 块数会从 1 变成几十到上万个。DiffViewer 的对齐（`alignChunk` 按块迭代，最多 8 轮）、块头、轨道标记的渲染成本**未测**。实施时必须在 GUI 中测量 3,000 / 10,000 行的未缓存切换与滚动，必要时设块数上限（超过时降级并提示）。
- 100,000 行超大文件的耗时从 47–88 ms 升到 187–677 ms（仍然明显快于去掉 scanLimit 的 3.8 s 以上）；可以先去掉公共前缀、后缀行，再改用 Int32Array 优化。

## 5. 方案

| 方案 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 分级 diff（推荐）** | `computeDiff` 改为第 4 节的“行级 → 区间内字符级”，保留区间级的 scanLimit / timeout 与总预算；超大区间只按行标记 | 修复退化；与 Git hunk 同一套行对齐，块操作基本都可用；最坏情况比现状更好（整体重写 500 行 335 → 29 ms），并且耗时有上限 | 新增约 80 行代码与单元测试；需要重跑 V1-06 文件切换测量，补做多块渲染的 GUI 测量；100,000 行文件变慢到数百毫秒，需要优化或设块数上限 |
| B. 保持现状，只提示退化 | 仍用 `scanLimit: 5000`；检测到单个 change 覆盖超过一定行数时，在工具栏说明“改动分散，已按整段显示，块操作不可用” | 改动最小，性能不变 | 问题本身没有解决：3,000 行以上、改动分散的文件仍无法逐块阅读，也无法做块操作 |
| C. 去掉 scanLimit，Worker 超时后回退 | 不设 scanLimit；超过 N ms 时终止 Worker 并重建，改用 `scanLimit: 5000` 重算 | 能算完的文件结果精确 | 结果随机器负载变化（同一文件有时有 65 块、有时只有 1 块）；超时就要多等 N ms 并重建 Worker；内存最高 +230 MiB；仍然需要 B 的提示 |

推荐 A：它是唯一一个既修复退化又不引入新的最坏情况的方案（**用户已选 A，见第 7 节**）。实施时的验收建议：lc4 夹具 65 块并且可以逐块暂存；3,000 / 10,000 行未缓存切换满足 ≤ 400 ms；整文件重写与 100,000 行场景有明确的耗时上限。

## 7. 实施结果（V2-D75，2026-09-29）

### 7.1 实现与原型的差别

`src/diff-core.ts` 的 `tieredDiff`（`computeDiff` 的返回结构不变）：

1. 先去掉公共前缀行与后缀行；
2. 行级：剔除只在一侧出现的行之后，以**两侧各出现一次的行为锚点**，取行号递增的最长链（patience diff），锚点之间的小段再用 `diff` 做行级比较，所有小段共用 200 ms 截止时间。原型直接对全部行做一次 `diff`，打乱行序的文件（整段移动）会先耗满 timeout 再进入不受约束的粗匹配；
3. 字符级：每个改动区间单独做 `diff`（`scanLimit: 5000`，区间 20 ms、总计 150 ms）；区间较短一侧超过 40,000 字符或预算用完时，两侧行数相同就逐行取公共前后缀（改动超过该行一半时整行标记），否则整段按行标记。原型在这种情况下直接整段标记，“忽略空白”对大段缩进变化就会失效；
4. 首尾相接的 change 合并为一处。

码点超出基本平面（不同的行超过约 6 万种）时，一行占两个码元，只接受编号相同且行号严格递增的行对。单元测试新增 7 项：lc4 夹具 65 块 / 120 处、整文件重写、7 万种不同的行、重复行、大段缩进 + 忽略空白、末行无换行，以及 300 轮随机文本（校验 change 能把左侧还原为右侧、块范围合法且递增）。前端测试 289 项全部通过。

### 7.2 diff 耗时（Node，`p-v2-10-scanlimit-probe.mjs`，中位数 ms）

| 3,000 行 lc4 | 2.9（**1**） | 9.1（65） |

### 7.3 阅读器（Windows GUI，`p-v2-10-gui.mjs`）

**块数变多后暴露的阅读器缺陷**：第一次 GUI 测量时，540 块的文件未缓存切换约 0.9 s、F7 约 0.66 s、滚动 P95 800 ms；1,813 块的文件切换约 3 s。CDP CPU 剖析定位到 `renderRailMarkers`：循环中每块读一次 `rail.clientHeight`，每次追加标记后都强制同步布局（O(块数²)），而且 contentDOM 的每次变化（滚动时渲染新行、F7 改选区）都会触发整批重建。修复方法：高度只读一次，用 DocumentFragment 一次插入；块、文档、轨道高度与设备像素比都不变时跳过重建（`src/DiffViewer.tsx`）。

测量方法：CDP 页面内测量（动作 → 断言首次成立 → 下一帧），滚轮为 CDP `Input.dispatchMouseEvent`，按键为页面内派发的 KeyboardEvent，1440×900；只操作本轮 `launchOris` 启动并核验的实例，不调用任何窗口激活 API。对照组为 main `d67ebf8` 的构建（这些文件都只有 1 块）。未缓存为每场景 6 份内容不同的副本（相互之间隔 2 个小文件，避开预取）；已缓存为 5 次；样本量少于 30，P95 即最大值。测量期间另一个会话也在运行 Oris GUI 测试，存在 CPU 争用，两轮修复后的数据都列出。

### 7.5 对齐收敛的后续修复（`fix/align-convergence`）

**做法**（`src/DiffViewer.tsx` 的 `installChangeAlignment`）：原先一轮对齐逐块推进，每块先调前缀间隔、等一次编辑器测量，再调下边间隔、再等一次测量，所以一轮至少要 2 × 块数次测量。现在一轮按文档顺序一次算出全部锚点、前缀与下边间隔：某个间隔高度变化 δ 时，其后所有边界都平移 δ（间隔的 `estimatedHeight` 就是其高度），因此“旧布局下的边界 + 前面已累计的变化量”就是逐块等待后看到的值。一轮只派发一次、等一次测量，再按实测误差决定是否进入下一轮（最多 8 轮，与原先相同）。锚点的规则不变：本轮有锚点时只保留当前锚点，没有锚点时保留已有锚点。另外，`alignedBoundary`、`roleHeight` 与连接带几何中的下边间隔查询改用按数组缓存的索引（按位置、按块与角色），避免每次查询都扫描全部间隔（一轮 O(块数²)）。

**验证**（Windows GUI，CDP 页面事件；对照组为 main `b7a20a9`，与修复构建先后连续测量）：

| --- | --- | --- | --- | --- |
| 3,000 行 lc4（65） | 91.7 → 56.5 ms | 2,233 → 73 ms | — / — | 33.3 → 16.8 ms |
| 3,000 行每 5 行（540） | 141 → 75 ms | > 30 s → 113 ms | 48 → 0 px | 41.6 → 25.0 ms |
| 3,000 行整文件缩进（273） | 167 → 75 ms | > 30 s → 271 ms | 24 → 0 px | 33.3 → 25.0 ms |
| 10,000 行每 50 行（182） | 85 → 62 ms | 6,105 → 77 ms | 0 / — | 25.0 → 16.7 ms |
| 10,000 行每 5 行（1,813） | 206 → 167 ms | > 30 s → 281 ms | 48 → 0 px | 58.3 → 66.6 ms |

“—”表示停下时视口内没有块（没有连接带）。

回归：

- `wrap-align-probe.mjs`：single 夹具（lc4 3,000 行，现为 65 块）视口内两侧同文行最大错位 4 → 0.9 px；“窗口宽度 +1 px 再恢复”触发完整重新对齐后为 97 px（7 个状态超过 1 px）→ 0.1 px（0 个），即 lc4 阶段 4 在 [wrap-align 结果](../validation/wrap-align-results.md)中登记的 97 px 错位也一并消除；multi 夹具（1,000 行 27 块）0 → 0.5 px，只出现在一个位置。修复后普遍残留约 0.1 px，在对齐自身 0.5 px 的收敛阈值之内。
- `v2-d58-font-equivalence.mjs --compare`：63 个状态中，只有“自动换行 + 对齐变化 · 右侧滚到 41%”这一个场景有差异，其余 6 个场景完全一致。该场景中两个构建对齐出的间隔不同，初始 scrollTop 本就不同（39036 / 38963）。逐步对比阅读位置：对照组在 7 次字号切换中，右侧顶部行在 1236 → 1235 → 1236 → 1232 之间漂移；修复后始终是第 1236 行，偏移为 47.8–50.5 px，**阅读位置更稳定**。
- `v1-05-acceptance.mjs --only reading`：37 项全部通过，其中包括“对齐开启时同一块两侧上下边误差 ≤ 1.5 px”。
- 前端测试 295 项、`tsc -b` 通过（jsdom 没有布局，对齐只能在 GUI 中验证）。

1,813 块的文件在对齐时滚动的帧间隔 P95 为 58 → 67 ms，这个场景修复前后都不理想，属于滚动本身的开销（不开对齐时也有 50–58 ms），不在本次范围内。
