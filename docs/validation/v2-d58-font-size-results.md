## 定位：一次字号切换的分段

场景与发布性能测试相同：3,000 行文件的并排 diff，右侧滚到 60%（scrollTop 约 32,800 px），页面内派发 Ctrl+= / Ctrl+-（CDP 事件，不是真实键盘）。新增 `scripts/perf/v2-d58-font-phases.mjs`：CDP Tracing 记录渲染主线程，按每次切换的时间窗口汇总各 rAF 回调（按注册调用栈归类）与其中的强制样式 / 布局、绘制；同时做 CPU 采样。压缩代码的位置用同一份源码构建的 sourcemap 映射回源文件（主包文件名中的内容哈希与被测构建一致）。

优化前（8 次，开 trace，P50 119.3 / P95 145.3 ms）：

| 阶段 | 每次平均（ms） | 说明 |
| --- | --- | --- |
| 设置写入与派发（keydown → 设置 store → React 提交） | 0.2 | — |
| CSS 变量生效（样式重算 7,481 个元素 + 布局 10,981 个对象） | 约 42 | 字号影响全部文本，无法省去；测量断言里的 `getComputedStyle` 把它提前到派发之后，真实使用时发生在下一帧 |
| CodeMirror 重新测量（两个编辑器各自的测量 rAF） | 82.9（其中强制样式 / 布局 46） | 每个编辑器 2 轮，每轮都按新视口重绘几乎全部行 |
| 同步滚动、外缘色标、对齐等 Oris 回调 | 约 5 | 未开启“对齐变化”时对齐不运行 |
| 块标题行与装饰 | 包含在 CodeMirror 重绘中 | 行装饰为静态装饰集，不随视口重建 |
| 绘制（PrePaint + Paint） | 19.6 | — |

CPU 采样中最大的一项是 `get anchorNode`（每次 55.9 ms）：CodeMirror 每轮重绘后读取 DOM 选区，这个 getter 在 WebView2 中会同步完成样式与布局。另用 `scripts/perf/v2-d58-dom-census.mjs` 统计一次切换中的 DOM 变更：`cm-gutters` 被整体摘下再挂回 4 次（CodeMirror 只在新旧视口重叠不到 80% 时这样做），高亮 span 的 class 被改写约 2,100 次。

**根因**：滚动在文件中部时，同一像素位置在新字号下对应的行相差很远（13 → 14 px 时约 7%，文件中部约一百多行，大于整个视口）。CodeMirror 第一轮测量按旧的像素位置选出一片完全不同的视口并整片重绘，再按滚动锚点修正位置，第二轮再把正确的区域整片重绘；两个编辑器各发生一次。所以文件顶部只要约 25 ms，文件中部却要 110–160 ms。一期 05 已经去掉了 Oris 自己引起的部分，剩下的就是这一项。

## 优化

`src/DiffViewer.tsx`：字号生效时（layout effect），不再只对编辑器请求重新测量，而是先按 CodeMirror 自己的锚点规则给出滚动快照（`view.scrollSnapshot()`：视口顶部那一行保持相同的像素偏移），CodeMirror 第一轮测量就按这一行选视口，只重绘一次。判断写成纯函数 `fontChangeScroll`（`src/diff-scroll.ts`）：

- 滚动在文件中部且没有自动换行：给出滚动快照；
- 在顶部（锚点为 0）、滚到底部（CodeMirror 锚定底部）、自动换行（各行折行数随字号变化、行高不按比例缩放，两种锚定的最终位置会差一行左右）：保持原来的只测量。

编辑器不重建；字号仍由宿主元素上的 CSS 变量决定，不派发 reconfigure。没有改变对齐、换行、块标题行、搜索的任何逻辑，也没有降低动画或精度。

第一版没有区分自动换行：对照脚本发现“自动换行”场景的最终位置与优化前差一行左右（优化前的构建自己跑两次完全一致），因此换行时改回原来的做法，见下一节。

## 与优化前一致性（阅读位置、对齐、换行、块标题行、搜索高亮）

新增 `scripts/perf/v2-d58-font-equivalence.mjs`：同一夹具上运行 9 个场景，每个场景依次切换字号 13 → 14 → 15 → 14 → 13 → 12 → 13，每次切换后（等 900 ms，开启对齐时再等对齐完成）记录每个可见编辑器顶部的行号、像素偏移、scrollTop、首行文本、字号，以及可见的块标题行、搜索命中数与当前命中、连接带数、对齐误差。

场景：并排右侧滚到 60%（右侧主控）；并排左侧滚到 30%（左侧主控）；并排滚到底部；并排顶部；自动换行（长行附近）；对齐变化；自动换行 + 对齐变化；搜索打开（命中高亮）；统一视图滚到 60%。

| 比较 | 状态数 | 结果 |
| --- | --- | --- |
| 优化前构建运行两次 | 63 | 只有 3 条相同的对齐误差（两次数值相同，见下），其余全部一致：优化前的行为是确定的 |
| 优化前 vs 验收构建 | 63 | 同上 3 条，其余**全部一致**（顶部行号、像素偏移 ≤ 1 px、scrollTop ≤ 1 px、首行文本、块标题行、搜索命中、连接带） |

那 3 条是“自动换行 + 对齐变化”场景中已有的对齐误差（滚到 41% 后初始 73.1 px，切换字号后 4 / 3 px），优化前构建两次运行数值相同，不是本次改动引起的；本阶段不处理，列入“未验证项”。

对照在两组构建上各做了一次：本阶段早期（main `37bc4e1` 与优化构建 `698EEA25…`）与合入前（v0.3.0 `6AC96660…` 与验收构建 `5D57C8F7…`），结果相同。
