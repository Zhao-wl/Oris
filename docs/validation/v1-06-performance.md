## 结论

- **S 数据集 24 项预算（时延 18 项、内存与资源 6 项）中 21 项达标、1 项未达标、1 项部分未达标（口径问题）、1 项未验证**：
  - **未达标：切换字号**（滚动到 3,000 行文件中部的并排 diff）P95 **160.4 ms**（预算 ≤ 100 ms，编辑器未重建）。同一场景的配色 94.2、主题模式 89.3 ms 达标；60 行文件中字号快捷键 25.8 ms。瓶颈与可选方案见“瓶颈与修复”，**需要体验取舍或预算调整，按规则停下来请用户决定，本轮没有修改产品代码**。
  - **部分未达标：失焦后内存**（`ORIS_WEBVIEW_MEMORY_TARGET=low` 强制级别，**不是真实焦点切换**）：静置 65 s 后 5 次全部达标（外部框架与工具 100.5–108.1 MiB ≤ 130，总开销 107.4–115.2 MiB ≤ 140）；切换刚结束 3 s 的“稳态”呈两种状态（约 53 / 99 MiB 或约 165–170 MiB），5 次中 2 次达标。A/B 显示 V2-01 构建同样如此，**不是代码退步**。
  - **未验证：外部变化 → 界面更新**（需要真实前台焦点，AGENTS.md 不允许抢焦点），手动步骤见文末。
  - 其余全部达标：首次打开 P95 404 ms、重启到显示快照 98.8 ms、热项目切换 33.8 ms、切换显示区域 33.8 ms 且不启动 Git 进程、文件切换 ≤ 36.9 ms、滚动帧间隔 10.4 ms、stage / unstage / commit、打开设置、5 项目分层内存、200 次混合切换峰值与静置、常驻 Git 子进程、缓存上限、10 项目对比。
- **L 数据集**（100,000 文件、100,000 提交、2,000 变化文件）：有界加载、可取消、不崩溃、内存有界全部满足；首次打开 P95 1.56 s；100,000 文件的 `git status` P50 165.8 / P95 170.6 ms（V2-D10 的数据）。
- **没有预先预算的写操作**（fetch、pull、merge、push、切换分支、stash、块操作）只记录数据，建议预算列为“待用户决定”。
- 负载：各套件外部进程 CPU 大多低于 10%；写操作套件本身触发 Windows Defender 实时扫描（见“负载记录”），按规则标“受干扰”的轮次单独统计，与未受干扰轮次的分布几乎相同。
- 发现但没有预算约束的问题：历史页打开过一次之后，每个改变 refs 的写操作都会在后台重读历史 3–4 次（每次操作多启动约 40–60 个 Git 进程），建议另行优化（待用户决定）。
- 本机为 47.7 GiB 内存，不是 16 GiB 参考机，未做换算；macOS 未运行。

## 瓶颈与修复

1. **切换字号（未达标）**。`appearance-probe.mjs --scrolled --trace`（4 次切换的渲染时间线）：每次切换约 19 次布局、21 次样式重算（合计约 75 ms），主要来自：
   - CodeMirror 的 `updateSelection → readSelectionRange`：两个编辑器各约 4 轮测量，每轮读取 DOM 选区时强制整页样式与布局，每次约 5 ms（每次切换约 8 次、约 42 ms）；
   - 字号改变后两侧行高变化，并排视图的对齐间隔需要重新计算（下一帧的 `refreshLayout`），触发第二轮测量；V2-05 的块标题行使块结构增多（阶段 2 已测到约 +17 ms）；
   - 测量断言本身读取 `getComputedStyle` 也会提前触发一次布局（约 14 ms，是把下一帧的工作提前，不是额外开销）。
   一期 05 已去掉 Oris 自身引起的部分（逐个编辑器 reconfigure、主题扩展重复生成、字号改为 CSS 变量，149.9 → 107.6 ms）。剩余开销在 CodeMirror 的测量 / 选区读取循环与并排对齐，没有找到只改实现、不影响体验的办法；可选方向都需要取舍（见待用户决定），**本轮未修改产品代码，也没有调整预算**。
2. **写操作后历史页重复重读（无预算约束，建议优化）**。历史页打开过一次之后即使切回“提交”页，每个改变 refs 的操作都会重读历史 3–4 次，每次约 12 个 Git 命令（`config` ×3、`for-each-ref` ×2、`log`、`rev-parse`、`show`、`diff-tree`、`remote`、`symbolic-ref` 等），相同命令重复出现。操作本身的时延不含这部分，但违背“只刷新受影响维度”的本意，且在大仓库中会占用后台 CPU。建议作为单独任务合并这些重读（待用户决定）。
3. **写操作触发 Defender 实时扫描**：fetch / pull / push / stash 在 `%TEMP%` 中写入对象与 pack 文件，Windows Defender（MsMpEng）与 svchost 随之占用 10–22% CPU。按规则计为外部负载；这是本机真实使用时同样会出现的开销，但不能通过添加排除项消除（不修改系统设置）。
4. **L 数据集打开时的 Git 子进程内存**：首次打开 L 时 Git 子进程私有工作集约 180–200 MiB（status 与统计），操作结束后回收；30 次重复打开后总开销短时 381 MiB。有界，不计入 S 预算，供 V2-D10 参考。

本轮新增的测量脚本（均只经 `launchOris` 启动并核验自己的实例）：`scripts/perf/release-perf-session.mjs`（负载监测下按顺序运行各套件、30 s 静置、受干扰重测）、`v1-06-write-latency.mjs`（没有预算的写操作时延与进程数）、`v1-06-git-children.mjs`（常驻 Git 子进程与回收）、`v1-06-large.mjs`（L 数据集界面）、`aggregate-release-perf.mjs`（汇总入库 JSON）。
