# 长链 lc5 阶段 3：超预算项的技术优化结果

日期：2026-09-30。任务：[长链 lc5](../tasks/onetime/long-chain-perf-lc5.md) 阶段 3。分支 `perf/optimize-lc5`（自 main `676a0c1`）。只验证 Windows。

## 结论

- **已知必做项：V2-D75 之后大文件的已缓存切换**（研究 10 §7.3 记录 182 块以上 P95 141–201 ms，超出 ≤ 100 ms）。优化后，同机交替 A/B（低负载，每场景每侧 120 次）**5 个场景全部达标**：1,813 块 P95 96.6 → 81.7 ms，其余 45.1–62.5 ms。改动都是不改变显示与交互的技术优化，没有调整预算，也没有体验取舍。
- **对研究 10 原结论的修正**：在低负载下，优化前的构建本身就只有 1,813 块略超预算（本次 A/B 为 P95 96.6 ms；上一组 A/B 的干净样本为 120.3 ms）；研究 10 当时的 141–201 ms 是在其他会话同时运行 Oris GUI 测试、存在 CPU 争用时测得的（研究 10 §7.3 已注明）。
- 第一轮优化（`b34ba90`）把块标题行放进初始编辑器状态，**反而使大文件变慢**（1,813 块 P95 120 → 231 ms），同机 A/B 发现后已定位根因并撤回（`ec849db`），见“撤回的一项”。
- 阶段 2 没有得到有效的性能数据（[阶段 2 报告](v1-06-performance-lc5.md)），因此没有“阶段 2 发现的其他超预算或回归项”可以处理；这些行在阶段 4 最终构建上复测。
- 回归：前端 43 个文件 318 项（新增 `DiffViewer.test.tsx` 4 项）、`tsc -b` 通过；界面 v1-05 reading 37/37、v2-05 functional 14/14、v2-06 `--skip-timing` 失败 0 项；v1-05 性能各段 A/B 没有退步。

## 耗时拆分（优化前，CDP 时间线）

`p-v2-10-gui.mjs --cached-only --trace <场景>`：从一个小文件切到目标大文件 10 次，用 `console.timeStamp` 标出每次切换的窗口，只统计窗口内的事件。540 块（3,000 行每 5 行）每次切换 107–188 ms，由三段组成：

1. **React 提交**（一个任务 55–106 ms，其中强制样式与布局 17–57 ms）：两个编辑器 `setState` 换入文档 → 各自 `dispatch(appendConfig)` 追加差异装饰 → 右侧派发块标题行（挂载时一次，随后 `hunkHeaders` effect 又派发一次相同的）→ 连接带、滚动同步、分栏宽度等控制器安装。
2. **下一帧**：`installSplitVisuals` 的 `measure`（18–40 ms，1,813 块时更多）+ 绘制 15–34 ms。
3. **再下一帧**：CodeMirror 自身测量后重绘行，MutationObserver 再触发一次 `measure`（10–28 ms）。

强制布局的来源（540 块，每次切换）：CodeMirror `readSelectionRange`（每次派发都会读 DOM 选区）约 12.7 ms / 6 次；`reuseOrCreate` 换入文档后写 `scrollTop = 0`（两个编辑器）约 10 ms；轨道标记读 `clientHeight` 约 7.7 ms；连接带 `draw` 读 `getBoundingClientRect` 约 7.5 ms；分栏宽度 `availableWidth` 约 6.7 ms。`measure` 中每块调用 6 次 `alignedBoundary`，对齐关闭时每次都新建一个空数组作为间隔规格，`specIndex` 的 WeakMap 缓存因此全部落空、每次新建两个 `Map`；边界表又把连接带已算过的上下边界重算一遍。语法解析（Lezer）在 CPU 剖析中占比大，但初始同步解析只覆盖视口附近 3,000 个字符、上限 20 ms，其余在切换完成后的空闲时段进行，不在测量窗口内。

## 优化（`b34ba90` + `ec849db`，`src/DiffViewer.tsx`）

| 改动 | 作用 |
| --- | --- |
| 差异装饰（修改行、词级）随 `EditorState.create` 一起创建（`buildSideDecorations` 改为按 `Text` 计算；单侧视图同样处理） | 每个编辑器少一次重新配置与派发（少一次选区读取与强制布局） |
| 复用的编辑器挂回后不再写 `scrollTop / scrollLeft = 0` | 在 WebView2 中实测：滚动容器摘下 DOM 再挂回，滚动位置本来就是 0（`artifacts/lc5/detached-scroll-check.mjs`），这两次写入只会强制同步布局 |
| 同一份块标题行已派发过时不再重复派发 | 切换文件时右侧原先派发两次相同的标题行（挂载时一次，`hunkHeaders` effect 一次），并各触发一次 `refreshLayout` |
| 对齐关闭时共用同一个空规格数组 `NO_SPECS` | `alignedBoundary` 不再每次新建 `[]`，`specIndex` 缓存生效 |
| `measure` 在同一轮里算出连接带几何与边界表 | 每块的上下边界只查询一次 |
| `installSplitResize`：写入 `--diff-left-width` 前只读一次可用宽度 | 原先写入后又读 3 次 `clientWidth`（样式失效后每次都要重新布局） |

显示与交互不变：装饰、块标题行、连接带、边界表的数值与原先相同；阅读位置恢复、块导航、滚动同步、字号 / 配色切换的逻辑未改。

### 撤回的一项：块标题行随初始状态创建

`b34ba90` 同时把右侧的块标题行（块级 widget）放进初始状态以省去一次派发。同机 A/B 显示所有大文件都变慢。时间线中提交阶段的布局从约 6 ms 升到约 45 ms；DOM 统计（`p-v2-10-gui.mjs` 的 `domAfterSwitch`）显示 1,813 块时右侧编辑器视口只有前 2,223 个字符（36 行），但 `viewportLineBlocks` 有 5,016 个，行号栏据此建了 5,017 个元素（优化前与左侧都是 36 / 37）。即初始状态中已有上千个块级 widget 时，CodeMirror 的视口行块列表会包含视口外的大量行块；创建后再派发则不会。诊断构建确认与同时做的“先在页面外换入文档再挂回”无关（该顺序也已恢复为原来的先挂回再换入）。`ec849db` 恢复挂载后派发，只保留“不重复派发同一份标题行”。

## 阶段 4 发现并修复的问题（分支 `perf/optimize-lc5b`）

| 1 | **打开工作区比普通项目首次打开多 367 ms**（P95 差，预算 ≤ 300；P50 差 460） | `workspace-acceptance.mjs --only perf-trace` 记录每次添加的 Git 进程起止：普通项目 14–15 个，工作区 70 个（列表可交互前 48 个）。① 共用 watcher 为 8 个成员**同时**启动 `ls-files -c -i --exclude-standard`，每个约 1.6 s，与打开父仓库重叠，父仓库 status 96 → 181 ms、`diff-files` 统计 0.2 → 1.8 s；② 增删统计与 rename 修正的 4 条 diff 命令没有带 `--ignore-submodules`，Git 进入 7 个子模块各跑一次 `status --porcelain=2 -uno`（每次打开多 18 个进程）；③ 成员发现约 33 个 Git 进程并行启动，在 Windows 上互相排队 | ① 各成员的清单在一个后台线程里依次计算（父仓库在前），watcher 建立时机与事件分类不变；② 统计命令使用与 status 相同的取值（V2-D80：开关关闭 `all`、打开 `dirty`），显示不变；③ 所选目录的路径与父仓库合并为一次 `rev-parse`，添加父仓库时不重复 `rev-parse`，`head_of` 两次查询并行，`ls-files -s` 与成员发现并行；分支 / HEAD 先读文件（同 V2-D53，拿不准时回退 Git），没有 `worktrees` 目录时不启动 `worktree list` | `49412af`、`fea5dd9`、`99739a9` |
